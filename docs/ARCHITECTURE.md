# StackStatus architecture

This document records how the app is put together and, first, what the live
status endpoints actually look like. Everything in the endpoint section was
verified against the real pages on 3 September 2026 with `curl`. These APIs are
public but undocumented and may change without notice.

## 1. Endpoint research

### 1.1 Atlassian Statuspage (Cloudflare, GitHub, Anthropic, Vercel)

| Vendor | Base URL | Notes |
|---|---|---|
| Cloudflare | `https://www.cloudflarestatus.com` | Served by Google Frontend. `summary.json` is about 210 KB because of the very long component list. |
| GitHub | `https://www.githubstatus.com` | Served by AtlassianEdge behind CloudFront, `cache-control: max-age=10`. |
| Anthropic | `https://status.claude.com` | `status.anthropic.com` now returns a 301 to `status.claude.com` for every path, so the bundled vendor uses the new host directly. |
| Vercel | `https://www.vercel-status.com` | AtlassianEdge, weak ETag. `vercel-status.com` without `www` is a 301. Verified 4 September 2026. |

Endpoints, all `GET`, all JSON:

- `/api/v2/status.json`: about 220 bytes. `status.indicator` is one of
  `none`, `minor`, `major`, `critical`, plus `maintenance` when a maintenance
  window is the only thing going on. This is the only request made on a normal
  poll.
- `/api/v2/incidents/unresolved.json`: 160 bytes when empty, a few KB per open
  incident. Fetched only when the indicator is not `none`.
- `/api/v2/scheduled-maintenances/active.json`: same shape, fetched only when
  the indicator is `maintenance`.
- `/api/v2/summary.json`: components plus incidents plus maintenances. Not used
  by the app because Cloudflare's copy is 210 KB, while the two endpoints above
  carry the same incident data in under 10 KB. This is a deliberate deviation
  from the brief, made on the numbers.
- `/history.atom` and `/history.rss`: incident history feeds, used by the
  generic feed adapter and by the platform detector as a fallback.

Conditional requests: every Statuspage endpoint returns a weak `ETag` and
answers `If-None-Match` with `304 Not Modified` and an empty body. Verified on
all three hosts.

Indicator mapping:

| Indicator | VendorState |
|---|---|
| `none` | `operational` |
| `minor` | `degraded` |
| `major` | `partialOutage` |
| `critical` | `majorOutage` |
| `maintenance` | `maintenance` |
| anything else | `unknown` |

Incident fields used: `id`, `name`, `status`, `impact`, `shortlink`,
`started_at`, `updated_at`, `resolved_at`.

### 1.2 incident.io (OpenAI)

`https://status.openai.com` is generated by incident.io (the Atom feed says
`<generator>incident.io</generator>`). Served by Vercel with
`cache-control: public, max-age=0, must-revalidate` and no `ETag`, so there is
no conditional request support. Bodies are small so this is acceptable.

Endpoints verified on `status.openai.com` and cross-checked on
`status.incident.io`, so they are generic to the platform rather than specific
to OpenAI:

- `/api/v1/summary`: about 150 bytes when quiet. Shape:
  `{page_title, page_url, ongoing_incidents[], in_progress_maintenances[],
  scheduled_maintenances[]}`. This is the polling endpoint.
- `/proxy/<host>`: the JSON the status page's own front end loads, about 10 KB.
  Contains `summary.components`, `summary.ongoing_incidents`,
  `summary.scheduled_maintenances` and the page structure. Used as a fallback
  if `/api/v1/summary` ever returns 404 for a page.
- `/proxy/<host>/incidents` and `/proxy/<host>/incidents/<id>`: incident
  history and detail. Not polled, but the detail shape is what
  `ongoing_incidents` entries look like: `{id, name, status,
  affected_components[{component_id, status, current_status}], updates[],
  published_at}`.
- `/api/v2/status.json` and `/api/v2/summary.json`: a Statuspage compatible
  layer. Present on OpenAI and incident.io's own page. The `summary.json`
  variant has no `incidents` key, so it is not a drop in replacement for the
  Statuspage adapter. Not used by the app.
- `/feed.atom`, `/feed.rss`, `/history.atom`, `/history.rss`: all serve the
  same feed. Entries carry `<b>Status: Resolved</b>` or the current status in
  the summary, which the feed adapter uses.

Vocabulary seen across 83 recorded OpenAI incidents:

- Incident `status`: `investigating`, `identified`, `monitoring`, `resolved`.
- Component status: `degraded_performance`, `partial_outage`, `full_outage`.

Mapping: the worst affected component status across ongoing incidents gives
the vendor state (`degraded_performance` to `degraded`, `partial_outage` to
`partialOutage`, `full_outage` to `majorOutage`). An ongoing incident with no
component statuses maps to `degraded`. A non empty `in_progress_maintenances`
with no incidents maps to `maintenance`.

### 1.3 Microsoft 365

Microsoft has no Statuspage or incident.io page and no anonymous JSON API for
tenant service health (that needs the Graph API with admin consent). The public
site `https://status.cloud.microsoft` is a JavaScript app. Reading its bundle
turned up these anonymous endpoints:

- `https://status.cloud.microsoft/api/feed/mac`: RSS 2.0, about 1 KB, with a
  non standard `<status>` element per item (`Available` when healthy). "mac"
  is the Microsoft 365 admin center. Per Microsoft's own description in the
  feed, it is only updated "when service issues are preventing tenant
  administrators from accessing Service health in the Microsoft 365 admin
  center". So it is a narrow signal: it catches the big ones, not every
  Exchange Online wobble.
- `https://status.cloud.microsoft/api/posts/mac`: the same data as JSON.
- `https://status.cloud.microsoft/api/posts/m365Consumer`: JSON array of
  consumer workloads (Outlook.com, OneDrive, Teams Free, Copilot and so on) with
  a `Status` per workload (`Operational`, `Service restored`, and degradation
  states).
- `https://rssfeed.azure.status.microsoft/en-us/status/feed/`: Azure, not
  Microsoft 365.

No `ETag` on any of these. The bundled Microsoft 365 vendor uses the feed
adapter against `/api/feed/mac`, and the README documents the limitation. A
dedicated Microsoft adapter reading the JSON endpoints is a candidate for a
later phase.

### 1.4 Feed adapter rules

The generic adapter parses RSS 2.0 and Atom with `XMLParser`. An item is
treated as an active incident when:

1. it has a `<status>` element whose value is not one of `Available`,
   `Operational`, `Resolved`, `Healthy`, `Service restored`; or
2. it has no `<status>` element, its date is within the last 24 hours, and
   neither its title nor its body matches a resolved marker (`Resolved`,
   `Completed`, `Status: Resolved`, `has been resolved`, `Service restored`).

Feed only vendors show as `degraded` while an item is active (`maintenance` if
the title mentions maintenance), because a feed cannot express severity.

### 1.5 Platform detection

`PlatformDetector` probes in this order and stops at the first hit:

1. `<base>/api/v1/summary` returns JSON with an `ongoing_incidents` key:
   `incidentio`.
2. `<base>/api/v2/status.json` returns JSON with `status.indicator`:
   `statuspage`.
3. `<base>/history.atom`, `<base>/feed.atom`, `<base>/feed.rss`,
   `<base>/rss`, `<base>/feed`, or the base URL itself with an XML content
   type: `feed`, with the discovered feed URL.
4. The base URL's HTML contains a
   `<link rel="alternate" type="application/(rss|atom)+xml" href="...">`:
   `feed`.

incident.io is checked before Statuspage because incident.io pages also serve
the Statuspage compatible endpoint.

## 2. Structure

```
StackStatus/
  App/          AppDelegate, StatusItemController, PopoverController
  Core/
    Models/     VendorState, Verdict, Vendor, Probe, Incident, FeedSnapshot
    Adapters/   StatusFeedAdapter, StatuspageAdapter, IncidentIOAdapter,
                FeedAdapter, PlatformDetector
    Probes/     Prober, HTTPSHeadProbe, TCPProbe, DNSProbe, BaselineProber
    Engine/     PollScheduler (actor), StateStore, VerdictEngine,
                VendorTracker (debounce), Notifier
    Persistence/ ConfigStore, ETagStore, HTTPClient
  UI/           Popover and Settings SwiftUI views
  Resources/    Assets, Info.plist, default vendors.json (generated)
```

### 2.1 Data flow

1. `PollScheduler` (an actor) owns the loop. It computes the next interval
   from user settings, vendor states, power source and sleep state, sleeps,
   then runs one cycle.
2. A cycle is a single `TaskGroup`: one child task per enabled vendor (feed
   fetch, then that vendor's probes) plus one for the three baseline probes.
   The group is raced against a 15 second deadline. Children that have not
   returned by then are cancelled and reported as `unknown`.
3. Each child returns a `VendorObservation`. The scheduler hands the batch to
   `StateStore` on the main actor.
4. `StateStore` runs each observation through that vendor's `VendorTracker`,
   a pure value type that implements the debounce rules and yields a
   `Transition` when a state is confirmed. Transitions go to `Notifier`.
5. `VerdictEngine.verdict(feed:probe:baseline:)` is a pure function over the
   three inputs. `VerdictEngine.headline(...)` folds the per vendor verdicts
   into the one line shown at the top of the popover and used for the icon
   colour.

### 2.2 Conditional requests and caching

`HTTPClient` wraps one `URLSession` with an ephemeral configuration, cookies
off, URL cache off, per request timeout 10 seconds, User-Agent
`StackStatus/<version> (+https://github.com/richhickson/StackStatus)`. It
consults `ETagStore` before each GET and sends `If-None-Match` when it has a
tag. On `304` it returns `.notModified` and the adapter returns `.unchanged`,
which the scheduler treats as "same as last time" without touching the UI.

`ETagStore` is in memory only. Persisting tags across launches would let the
first poll after launch return `304` with no cached body to fall back on, so
tags live exactly as long as the parsed snapshot they belong to.

### 2.3 Backoff

Per vendor. A `429` or `5xx` from a status page sets `retryAfter` from the
`Retry-After` header if present, otherwise `2^n` times the user interval,
capped at 30 minutes. While a vendor is backing off it is skipped in the cycle
and keeps its last known state.

### 2.4 Adaptive interval

| Condition | Interval |
|---|---|
| All vendors operational, on mains | user setting (default 5 min) |
| Any vendor not operational | 2 min |
| On battery, no active incident | user setting times 3 |
| System asleep | paused; one immediate poll on wake |

### 2.5 Files on disk

The app is sandboxed, so Application Support resolves inside its container:
`~/Library/Containers/com.helpfullyit.stackstatus/Data/Library/Application Support/StackStatus/vendors.json`.
The brief's `~/Library/Application Support/StackStatus/vendors.json` is the
same location from the app's point of view. Preferences live in the standard
`com.helpfullyit.stackstatus` defaults domain.

### 2.6 Debug aids

- `StackStatus --once` runs one poll cycle headlessly, prints every vendor's
  state, verdict, probes and the baseline, and exits.
- `STACKSTATUS_DEBUG_INTERVAL=<seconds>` overrides the poll interval.
- `STACKSTATUS_DEBUG_SHOW_POPOVER=1` opens the popover after the first poll.
- `STACKSTATUS_DEBUG_SNAPSHOT=<name.png>` renders the popover to a PNG in the
  container's temporary directory after the first poll and quits.
- Debug builds print each notification to stderr as it is posted.
- `Scripts/fixture-server.py` is a fake Statuspage whose state you flip with
  `curl`. `NSAllowsLocalNetworking` is set in Info.plist so the app can talk
  to it over plain HTTP on 127.0.0.1.

### 2.7 Self update

Opt in. `UpdateMonitor` follows the `checkForUpdates` setting: while on it
sends a conditional GET to `api.github.com/repos/richhickson/StackStatus/releases/latest`
20 seconds after launch and then daily; Check now sends one on demand. A
release whose tag is numerically newer than `CFBundleShortVersionString`
shows a banner in the popover.

`UpdateInstaller` downloads `StackStatus.zip` from the release, extracts it
with `ditto` inside the container, and checks it with the Security framework
against the requirement `anchor apple generic and certificate leaf[subject.OU]
= "DFL38M27U3"` with nested code and all architectures, plus a bundle
identifier and version match.

It then hands the zip to `StackStatusInstaller.xpc`, an embedded XPC service
that is deliberately not sandboxed. Two facts force this: the sandbox stamps
every file the app writes with a quarantine flag (`0086`, "created by an
AppSandbox"), and LaunchServices refuses to execute a bundle carrying that
flag, even from Finder. Sparkle solves it the same way. The helper extracts
the zip afresh, runs the same signature and identity checks, strips the
quarantine attribute, moves the old bundle aside, moves the new one in,
deletes the old one, and runs `open -n` on the new copy. The app quits when
the helper replies. The helper accepts connections only from a bundle with
identifier `com.helpfullyit.stackstatus` signed by the same team.

### 2.8 Debounce and notifications

`VendorTracker` confirms a new state after two consecutive polls, except
`majorOutage` which is confirmed immediately. `unknown` never confirms, never
notifies and never resets the pending count, so a single timeout in the middle
of an incident does not produce a spurious "resolved".

Baseline is tracked the same way: two consecutive failed baseline polls
produce one "your connection looks down" notification. Recovery is silent.

Quiet hours suppress the notification but not the icon or the transition.
